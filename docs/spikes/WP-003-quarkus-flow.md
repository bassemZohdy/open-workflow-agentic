# WP-003 Spike A: Quarkus Flow 1.2.0 capabilities

**Version:** 0.1 · **Date:** 2026-10-18 · **Status:** Findings, not yet reviewed by the owner

Code: removed (issue #30). The spike was temporary, was never part of the root build or the product, and only its outcomes are kept here; the code is in git history at `b76181d` under `spikes/`. The product work package builds and tests the real implementation. Decision: [ADR 0019](../adr/0019-how-workflow-instances-are-started-queried-cancelled-and-resumed.md).

## How to read the evidence

- **verified-by-test**: a test in the spike runs against the real engine and passes (or is `@Disabled` with the observed failure). The test name is given.
- **read-in-docs**: taken from the Quarkus Flow documentation or from the Serverless Workflow SDK source code. Not run here.
- **unknown**: not established by test or documentation.

The engine used is Quarkus Flow 1.2.0 with Serverless Workflow SDK 7.35.3, Quarkus 3.39.5, Java 21, PostgreSQL 16 (database `spike_a`).

Two facts changed how the spike was run, and both affect the plan:

1. Quarkus Flow's HTTP client retries failed calls three times by default. This sits below the OWS retry policy (Q08).
2. Quarkus Flow restores persisted instances at startup but does not start them. Restored instances are PENDING and never resume on their own (Q02, Q11).

## Facts the plan did not know

These came up during the runs and change the design. Each is verified by a test or by the named source line.

1. **Restored instances are not started.** A kill -9 while waiting leaves the instance registered as active in PENDING. Nothing resumes it, including the periodic scan. `quarkus.flow.persistence.scan-interval` was tested: the scan finds the instance but skips it, because it is already registered active. Only an explicit `start()` on the in-memory object resumes it. The docs say restore resumes "from their last checkpoint"; this does not happen in 1.2.0 for waiting instances.
2. **The persisted row has no status while waiting.** Only `SUSPENDED` is written by `writeStatus`. `WAITING` is in memory only. So a database query cannot tell a waiting instance from a running one.
3. **Completed and cancelled instances are deleted.** `completed`, `failed` and `aborted` all call `removeProcessInstance`, which deletes the instance row. Our operations API cannot query history from the Flow tables; history has to come from our own audit or task records.
4. **The HTTP client retries below the workflow.** See Q08. Any `call: http` to a non-idempotent endpoint is repeated up to three times by default.
5. **A timed-out call can write after its instance is gone.** A task that times out keeps running in the background, and when it finishes its persistence write can violate the foreign key from `taskinfoentity` to `workflowinstanceentity` (seen in the in-process run). The write is logged, not retried.
6. **Event delivery is not durable for `listen ... one`.** Events go to in-process registrations (`InMemoryEvents`). An event published while no listener is registered is lost (Q02).
7. **Packaged startup can race the warm-up.** In the packaged jar the definition warm-up runs on a thread that can start after the listener. A restore that begins too early finds no CDI container and silently registers nothing (`ArC container not initialized`). The spike waits for `Workflow definitions warmup complete` before using an app.
8. **The engine ships no instance REST API.** Start, query, cancel and resume are ours to write (ADR 0019).
9. **The published Flow DDL does not match the entities.** Applying the docs' PostgreSQL script through Flyway does not satisfy the engine (Q06). WP-105's "Flyway owns the schema" plan needs the entity-matching DDL, or the Hibernate-generated schema reviewed and frozen, before production (ADR 0011 already says generation must be replaced).

## What this means for the plan

Work packages whose assumptions are now wrong or newly risky:

- **WP-105 Run lifecycle and canonical progress (XL, critical path).** The plan says the Flow instance is "canonical for process progress" and that Flow persistence and db-scheduler provide restart. Restored instances do not run without an explicit start (fact 1), so the reconciler must start them. This is the largest single change. Add to WP-105: an explicit resume step at startup, and a reconciler that finds PENDING restored instances. Re-size WP-105 upward.
- **WP-109 Timers, deadlines and durable failover (L).** Listen deadlines are re-armed from resume, not from the original start (Q03). A deadline therefore grows across every restart. Store the absolute deadline in our own table (db-scheduler or the agent_task row) and enforce it, instead of relying on the Flow timeout alone. Also: the Kubernetes lease behaviour (Q07) is read in docs only, so WP-109's failover test is the first real evidence.
- **WP-108 Effect ledger and compensation (L).** Q08 and Q11 show that a non-idempotent effect can run more than once, both through the HTTP client retry and through a restart. The ledger's intent-then-outcome design is needed for every external call. Do not rely on Flow retries for exactly-once.
- **WP-107 Event correlation and idempotent inbox (M).** Events are not buffered for `listen ... one` (fact 6). The CloudEvents endpoint must persist events itself before any listener is registered, and the inbox must replay them.
- **WP-106 Human task service (L).** Human approvals wait on `listen`. A human decision that arrives during a restart window will be lost unless it is stored first (fact 6). Bind human tasks to our own durable table, not to the Flow wait alone.
- **WP-302 Version pinning of in-flight work (L).** The plan reuses "Flow definition versions". Two versions run side by side (Q04), but the instance row is keyed by (application id, instance id); the definition version is an ordinary column (`WorkflowInstanceKey`). A lookup by id alone can return an instance of another version (pinned in `Q04_twoVersionsRunAtTheSameTime`). Pinning has to store the definition id and version in our own registry and check it on every lookup.
- **WP-301 and WP-603 (inventory and operator console).** Completed and cancelled instances disappear from Flow (fact 3), and a waiting instance has no persisted status (fact 2). Operations views must come from our task and audit records.
- **WP-604 and WP-605 (not affected yet).** No change.

The planned use of `quarkus-flow-jpa` (WP-105, WP-106) holds, with the restrictions above. The planned use of `quarkus-flow-durable-kubernetes` (WP-109) is unverified.

## Open questions

- **Q07 is unverified.** The lease durability claim needs a cluster run. Need a decision on whether WP-109 runs a Kubernetes test in CI or only in a dev cluster.
- **Does the Flow JPA DDL script in the docs match the jar's entities?** The docs claim scripts exist; the 1.2.0 jar does not contain them. Need the upstream source or a diff of the docs script against the Hibernate-generated schema.
- **Identity (Q10).** Not tested. The spike has no security extension. Need a separate test with `quarkus-flow-oidc` and token propagation.
- **Does a newer Quarkus Flow release fix the restore gap?** Recorded against 1.2.0 only. The gap should be re-tested on each upgrade (WP-402).
- **Upstream report.** The restore gap (fact 1) and the HTTP client retry default (fact 4) look like upstream issues. Not reported. Owner decides whether to file them.
- **Is the warm-up race (fact 7) specific to this packaging?** Seen with `quarkus-run.jar` on this host; not tested with a native image or on a different JVM.
