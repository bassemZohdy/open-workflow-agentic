# WP-107 literal match-set preparation

Owner: GPT. Reviewer: Claude. Status: partial, not wired to a production consumer; WP-107 and T13 remain open.

The selector derives slots from the exact retained snapshot and verifies the group's strategy and filter fingerprints. It evaluates only literal CloudEvent `type`, `id`, `subject`, `datacontenttype`, source URI and data-schema URI filters without calling SDK predicates, modifying workflow metadata, or invoking callbacks. It refuses correlations, expressions, URI templates and other properties. Explicit untyped filters are refused because the pinned SDK turns a null-type registration into an unconditional broadcast. `ANY []` uses a wildcard slot; simultaneous data and stop wildcards are refused because the in-memory SDK has only one broadcast registration. The tests compare supported literal type, ID, content type, source, data schema and wildcard paths with the pinned SDK's actual in-memory consumer. This limited subset is not general SDK conformance; unsupported inputs must fail closed, with no unfiltered fallback.

The selector produces an immutable result bound to the group and receipt. The public group-store method accepts only that result. V81 adds the complete pre-classification match fingerprint to each newly retained selection, including both data and until matches, and rejects a replay whose full set differs even when the classified winner is unchanged. V81 retains old rows without a fingerprint; their replay is refused because the full set cannot be reconstructed. Classified memberships remain unchanged. The package-private raw store entry point is used by component tests, not as a production selector.

Local verification used the focused runtime tests and PostgreSQL 16.15 group-store tests in a separate database. These cover duplicate filters, data/until overlap, SDK matching for a literal filter, refusal of unsupported cases, group/receipt binding, retained replay identity, and the existing lease and storage component cases. A separate upgrade rehearsal preserves a synthetic pre-V81 row and rejects new rows lacking a complete-match fingerprint. A storage test simulates a legacy row in its disposable database and verifies that historical selection remains readable while replay is refused; it does not execute replay on an actual upgraded production row. The tests do not prove general expression or correlation evaluation, deployed database grants, production route authorization, complete consumer integration, or T13. The trusted coordinator must validate approved routes and current authority, preserve FIFO and recovery semantics, and fence callbacks. The proposed V81 SQL is outside the default Flyway path; a test-resource copy is applied only in a dedicated test database. Deployment activation, migration ordering and database grants need review before the store is used.

The follow-up `ListenCompleteMatchMigrationTest.realPreUpgradeSelectionRemainsReadableButCannotBeReplayed`
creates an actual scoped registry instance, live inbox task claim, registered group, retained CloudEvent and
pre-V81 selection in a disposable PostgreSQL 16 database. The legacy transaction uses the pre-V81 columns
with owner, pinning, membership, foreign-key and immutable-history triggers enabled; it does not claim to run
the historical Java binary. After applying the proposed V81 through Flyway, the current store reads the same
receipt and membership, refuses replay through the public selector path, and retains the original selection.
Three migration tests passed locally without skips. This proves the isolated upgrade path, not deployed role
grants, migration activation, SDK callback/Flow recovery, or T13; exact-head CI and independent review remain.
