# WP-106: checkpoint recovery in separate processes

The isolated PostgreSQL test stages an audited human decision, delivers its exact retained event to the pinned SDK, and waits for the real JPA task checkpoint and matching receipt proof. It stops the original workflow component at that point. A separate JVM reads the retained registry row, uses the actual JDBC checkpoint recovery and audit trail, commits the acknowledgement, and halts without running cleanup. A second fresh JVM retries recovery. The test checks one acknowledgement audit, no new reservation, then restores the saved workflow with the real JPA reader and reconciler and verifies that it resumes after the listen without registering it again.

The four `HumanWakeCheckpointTest` cases passed against PostgreSQL 16 on Linux, with no skips. This is a test-only delivery callback and fixture authorization; it is not an activated human-task service or production authorization. The original checkpoint-writer JVM is still alive, and the workflow restoration runs in that original process. The test therefore does not prove a writer-process crash after checkpoint, a full application restart, or recovery if a process dies after audit commit but before acknowledgement. Production dispatch and authorized replay, task lifecycle and the complete T02 acceptance test remain open.
