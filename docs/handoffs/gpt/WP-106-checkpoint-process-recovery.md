# WP-106: checkpoint recovery across processes

Checkpoint recovery now appends its `event.checkpoint.observed` audit and changes the delivery to `ACKNOWLEDGED` in one local PostgreSQL transaction. It first locks and checks the pinned registry instance and retained receipt, then appends the audit and updates the delivery on that same connection. A failed audit, update, or transaction rolls both back. Concurrent recovery sees an existing acknowledgement and does not append a second audit. A lost commit reply is resolved by retrying against the retained acknowledgement; it is not treated as proof that a commit failed.

The isolated human test stages an audited decision, delivers its exact retained event to the pinned SDK, and waits for the real JPA task checkpoint and matching receipt proof. A separate JVM appends the recovery audit and halts before updating the acknowledgement: both writes remain absent while the checkpoint remains consumed. A fresh process then repairs the receipt and halts after commit; a third retries without a second audit. The original process uses the real JPA reader and reconciler to resume after the saved listen without redelivery. Separate PostgreSQL tests cover rollback after audit insertion, concurrent recovery, mismatched retained facts and audit failure.

This transaction assumes the audit and inbox tables are on the same PostgreSQL datasource and that its runtime role can append to the audit chain and update deliveries. The audit chain lock is held until the acknowledgement transaction commits, so contention can delay recovery; failure keeps recovery closed. The acknowledgement is local audit evidence, not proof of remote audit delivery, chain verification, caller authority or permission to dispatch.

The callback and human authorization in the checkpoint test are fixtures. In the separate recovery-worker test, the original checkpoint-writer JVM remains alive and workflow restoration occurs within it. Production dispatch, authorized replay, task lifecycle and complete T02/T13 remain open.

The process-restart case runs the actual test application in a separate JVM using an isolated shared database. The writer stages a fixture-authorized human decision, delivers the selected event through a test-only callback, verifies the real JPA task checkpoint and receipt, and halts immediately before acknowledgement. A fresh application JVM reads the retained registry and checkpoint, repairs the acknowledgement, restores through the real JPA reader and reconciler, and reaches the following task without registering the completed listen again. The database and a supervising test process stay alive. This verifies an abrupt application-process exit after a committed checkpoint, not machine or database failure, an activated production human dispatcher, or full T02.

Owned delivery now retains the original audit event id and time in an immutable source tied to the actual checkpoint proof. Its audit append is idempotent and runs outside the inbox row lock; recovery uses the same source and validates an existing event and head before acknowledging. Concurrent owned attempts, the owned/recovery race, and an owned process exit after audit commit but before acknowledgement reuse one event. V77.7 adds the retained source table; deployment must grant the appropriate inbox and audit permissions. The older claim-based JdbcInboxDispatch acknowledgement path is separate and does not gain this guarantee. Historical acknowledgements are not backfilled or rewritten.

The additive [checkpoint audit grant template](../../../deploy/checkpoint-audit-roles.md) has now been exercised with a fresh restricted PostgreSQL role. It does not configure the other owned-delivery permissions or prove the effective privileges of any deployed identity.
