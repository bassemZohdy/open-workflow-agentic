# WP-106: explicit targeted human wake dispatch

`HumanWakeDispatcher` composes the existing isolated human-decision journal, staged reference event, owned inbox reservation and SDK checkpoint marker for one captured SDK registration. It verifies the exact application, workflow, task position and iteration, rejects correlation predicates, evaluates the actual SDK predicate, stages only a matching retained decision, reserves under the current task claim, installs the marker, and checks the registration and live claim again before invoking that one callback. It does not broadcast the event. A bounded in-process gate prevents concurrent calls for the same task through one dispatcher instance; durable reservations and the checkpoint fence remain necessary across instances and processes.

`DISPATCHED` means only that the callback returned; the actual SDK task checkpoint and receipt proof, acknowledgement and post-checkpoint authority gate must still succeed before continuation. A failed or uncertain reservation is not automatically retried under the same owner epoch. The caller must use the same approved datasource for the stage, owner and guarded JPA writer and supply the actual live registration. This is an explicit prototype against `human_proposal`, with no CDI, endpoint or scheduler wiring. It does not authenticate an actor, approve a decision, establish current workflow owner authority or supply an approved production policy, listener registry or production human-task schema.

The application test uses the real SDK and JPA writer with fixture approval: it proves a registration for another instance is refused without staging, concurrent calls to the same task return BUSY, the selected callback creates a real checkpoint and does not wake the other instance, and a claim released during blocking reservation audit prevents the callback and checkpoint. Existing separate-process tests continue to exercise checkpoint recovery, but the new dispatcher itself is not production-wired or an end-to-end T02 proof. General listen strategies, production authorization, distributed callback coordination and supported recovery/activation remain open.

An isolated process test now also stops the dispatcher owner immediately after the reservation audit commits and before its callback. A fresh application process uses the original JPA reader and reconciler to restore the waiting listen, waits for a new claim, refuses the old claim, dispatches the same retained event on attempt two, and verifies one following-task start, a real checkpoint and one acknowledgement. The database and supervisor remain alive; the caller, policy and captured listener are still fixtures, not automated production replay.

`HumanWakeRegistrations` is an explicitly composed bounded SDK consumer wrapper. It captures a single human-type listener per application, engine, definition and task occurrence without registering that listener for the delegate's type broadcast. The dispatcher checks a revocable handle before and after blocking steps and serializes callback start with SDK unregister; an already-started callback may finish, and its slot stays occupied until it does. A process-recovery test locates the newly restored listener through this wrapper. Other publishers and wildcard listeners are outside this wrapper's guarantees. The in-memory capture is not tenant or producer authorization, a durable lease, a production registration service, or a replacement for checkpoint fencing.

V77.8 retains the complete wait identity in PostgreSQL when registration commits. `findProfile` reconstructs the wait, checks its digest and registry binding, and returns data only. The separate-process human tests now read the wait key from the retained decision and reconstruct the wait from this profile instead of copying position and iteration through the test manifest. Old digest-only waits have no inferred profile; an exact re-registration can populate one without changing its deadline. The listener configuration remains a test fixture, and a profile is not caller, policy or lease authority. [Additive restricted-role grants](../../../deploy/wait-profile-roles.md) were exercised in a disposable database; deployed permissions remain unverified.

`HumanWakeRecovery` is an explicitly constructed isolated-schema data reader. Given a tenant and decision ID, it reconstructs the retained decision and wait, verifies the decision fingerprint, task and original audit binding, and classifies blocked, staged, checkpointed, acknowledged or terminal state using the retained signal and checkpoint proof. Missing profiles and changed decision content are refused. Its string representation does not include private decision content. The process-restart tests now recover the decision as well as the wait from PostgreSQL; test IDs, listener configuration and authorization remain fixtures. Callers must separately establish internal access and replay authority; the reader provides no production discovery, policy, scheduling or activation.

The reader also offers a bounded tenant-scoped scan of retained decision IDs, in key order with an exclusive cursor. It includes terminal records and does not hide rows whose other retained data is missing; each ID must be loaded and classified separately. The scan neither claims work nor checks authority. It is not a snapshot: concurrent inserts can sort before the cursor, so a scheduler must periodically restart at the beginning, bound work fairly, authorize access and coordinate claims. No scheduler or production discovery permissions are activated here.

In both abrupt-process restart tests, the supervisor now passes only the workflow instance and application identifiers to the new process. It pages through the tenant scan and loads retained decisions to find the test workflow, then exercises the existing reservation or checkpoint recovery path. This is test-driven discovery for a single known workflow, not an active production scheduler, cross-replica claim protocol, or authority check; listener configuration and authorization remain fixtures.
