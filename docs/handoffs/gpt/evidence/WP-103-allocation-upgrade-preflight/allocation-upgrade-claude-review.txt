**What I checked in the SQL and tests:**
- **V77 baseline:**

- **Inventory and NOT VALID FK:**
  - **Inventory:** The immutable inventory captures call key, entry, contract, epoch, executor and time. INSERT, UPDATE, DELETE and TRUNCATE on it are refused with 42501, naming that table.
  - **Insert guard:** The existing allocation insert guard still refuses retrofitting an allocation (23514) once an execution exists for the call.

- **Concurrent writer:** The lock is `SHARE ROW EXCLUSIVE`, taken before the inventory read, under READ COMMITTED. The test confirms the migration is genuinely waiting on the lock (`pg_locks`, not granted) while an uncommitted writer holds a row. After the writer commits, its key is in the inventory.
- **Isolation, timeouts, rollback:**
  - **Isolation:** A SERIALIZABLE caller is refused with 25001 before any DDL, with no downgrade.
  - **Timeouts:** The lock-timeout cap is 2s and the statement cap 5s. Stricter 100ms/500ms values are retained after commit, and the search path is restored.
  - **Failure handling:** A lock timeout gives 55P03 in under 3s with no partial schema. A conflicting pre-existing allocation table keeps its marker row, and no functions or inventory remain.
- **Catalog pinning:** All new functions pin `search_path = pg_catalog, pg_temp`. The test shows a hostile `public.sha256` and a `pg_temp.text` domain do not change the digest. The in-suite control that drops the pin fails or gives a different digest, then is rolled back.
- **No fake backfill:** The insert into the inventory only copies existing execution facts, and nothing is inserted into the allocation table.

**Material findings (none blocking this rehearsal):**
1. **Statement timeout is never exercised.** The tests only show that stricter values survive, never that the 5s cap actually fires. A multi-statement simple-protocol string may be timed as a single statement, so the cap's behaviour depends on how the runner executes the file. pgjdbc and psql send statements separately, so this is likely fine. Add a test or a runner note before any activation.
2. **Other locks are unproven.** The lock-wait tests only cover `task.resource_execution`. Creating the new table's FKs also locks `resource_call`, `agent_task` and `delegation_grant`. Those waits are bounded by the 2s cap and roll back the whole transaction, but they are untested.
3. **Handoff wording.** The 55P03 test sets a 100ms lock timeout for the migration session, so it is a bounded-failure test rather than a test of the 2s default.
4. **Unproven functions.** The new-7 functions reused from the stale proposal are not claimed fully verified. This rehearsal only checks their hashes, not their guard behaviour. For example, the insert-guard branches for parent, grant ancestry and expiry are not covered.
