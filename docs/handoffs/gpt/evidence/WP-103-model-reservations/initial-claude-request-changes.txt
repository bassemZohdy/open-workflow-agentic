## Blocking finding
**Stale snapshot under inherited REPEATABLE READ.**
- **What happens:** `reserve()` and the V79 insert guard serialize on `select … for update` of the `task.instance` row. They then `sum(held_micros)` over the account. The code deliberately preserves inherited write isolation. Under REPEATABLE READ the snapshot is taken before the lock wait, so the sum misses a sibling hold that committed while waiting.
- **What I checked:** a two-session psql experiment on a scratch DB, since dropped. Post-lock `sum` returned 0 while a fresh transaction saw 1000. I did not exercise it through the gate itself.
- **Impact:** two sibling allocations under one parent account could both pass the `root_held` and ceiling check, and the parent cap could be exceeded. `unique(allocation_key, ordinal)` and the node primary key still protect the per-leaf count and same-node reuse. The comment "READ COMMITTED after the serialization wait" is only true at READ COMMITTED.
- **Test gap:** no test runs concurrent writes under REPEATABLE READ or SERIALIZABLE. The SERIALIZABLE test is a single sequential node. SERIALIZABLE should fail closed through SSI, but that is also untested.
- **Fix:** make the reserving write refuse REPEATABLE READ, either in the Java transaction or in the insert guard via `transaction_isolation`. Alternatively require READ COMMITTED for that transaction. Then add a concurrent sibling test under each isolation level.

## Non-blocking findings and residuals
- **V79 atomicity:** the gate checks isolation, not that an explicit transaction block surrounds it. A per-statement autocommit runner would pass the check and apply objects piecemeal. This is a precondition, not enforced.
- **Concurrency tests:** there is no true concurrent test across sibling allocations or the parent cap. The sibling test is sequential.
- **Lock contention:** each `requireCurrent` re-locks the instance row (`for update`). That adds contention and a 2s lock-timeout risk. A late timeout withholds output after the closure already ran, which is safe but costs availability.
- **Hierarchy depth:** accounts anchor only to the immediate parent task or root allocation. Grandparent-level aggregation is not enforced, so it sits with the "other budget categories" residuals.
- **Deletion tamper evidence:** deleting a tail reservation by bypassing the triggers (`session_replication_role=replica`, as the test's `corrupt()` does) is undetectable. Deleting a middle row trips the ordinal uniqueness check.
- **Function execute grants:** PUBLIC retains EXECUTE on the 9 new functions. This is harmless under SECURITY INVOKER with table privileges revoked, and the PUBLIC clearing is tested for tables only.
