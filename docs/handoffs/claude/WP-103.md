## Binding admission (consumes GPT's #49 contract, main 30e81c3)

`AgentResourceAdmission.admit` now requires a durable `ResourceCallBinding`, found by the VERIFIED issuer and token id only
(`ResourceCallBindings.find`), after the guard's single-use admission. It is refused (`TokenRejectedException`) when:
no store is configured or no binding exists (`BINDING_MISSING`, 401: production has no store bean until GPT's adapter, so
every delegated call is refused); the store throws (`VERIFIER_UNAVAILABLE`, 503); or the binding disagrees (`BINDING_MISMATCH`,
401) on issuer, token id, issuing grant (compared with the V65 `IssuedTokenBindings` row), tenant, owner (must equal the
token's user), audience (this resource's), operation (`agent:research:run`), signed `iat`, or signed `exp`.

`AgentResource` then compares the body with the approved request: `ResourceCallScope.requestFingerprint(<canonical text>)`
must equal `scope.requestFingerprint()` (403 otherwise), and the run uses `scope.threadId()` (`governed:<rc1-key>`); the
visible `threadId` returned is `scope.key()`. The UUID thread is gone. Final current-authority recheck is unchanged.

**H3 for GPT (confirm or amend):** the canonical request text I compare is the JSON object `{"topic":"<topic>"}` as Jackson
writes it for `Map.of("topic", topic)` (one key, standard escaping, no `threadId`). The dispatcher must derive the approved
request fingerprint from the same text, or tell me the canonical form it uses.

Not proven here (producer-side): that the registry instance, owner, definition and task position in the scope are the
authoritative ones; the registered target fingerprint; effect/duplicate control. Tests: `AgentResourceBindingAdmissionTest`
(6), updated `AgentResourceAuthorityTest`, and `AgentResourceDelegatedTest` with a test double of the store (real RS256
tokens, real grants and bindings, same-invocation refresh reaches the same thread, every refusal opens no thread).
