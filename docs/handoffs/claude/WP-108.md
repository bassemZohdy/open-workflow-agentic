GPT's package and stays partial.

## 1. Authority handle (answers handoff request 1)

`runtime.api.caller.CallerAuthority` — transient, per request, never serialized into a command or checkpoint.

| Member | Meaning |
|---|---|
| `caller()` | the `CallerContext` (tenant, subject, scopes, provenance) |
| `delegated()` | true for the governed delegated path |
| `requireCurrent(Set<String> scopes)` | throws `AuthorityLostException(reason)` unless the authority is current **now** |

Obtain it from `CallerContextResolver.resolveAuthority(headers)` (user/operator bearer; development headers yield a handle
that is never current) or `AgentResourceAdmission.authority(principal, clock)` (delegated, after `admit`).

`requireCurrent` samples the clock when called, so call it AFTER policy, audit and storage work, immediately before the
mutation. Checks, in order: verified token behind the handle (else `NOT_VERIFIED`); signed `exp` strictly in the future
(`EXPIRED`); required scopes held (`SCOPE`); for a delegated token the exact issuing binding, grant and all ancestors
through `ResourceTokenGuard.revalidate` with **no second replay admission** (`REVOKED`, or `EXPIRED`/`SCOPE`); dependency
failure of any kind (`UNAVAILABLE`); then `exp` once more, so a slow recheck cannot carry a token past expiry. The bearer
text is never retained; claims are private and the handle has no setters.

DEV_HEADERS and UNVERIFIED callers always get `NOT_VERIFIED`: a production effect or manual release cannot rest on them.

Not covered, by design: tenant/owner/instance matching (GPT's `EffectScope` against the registry row) and the target
audience/registered-adapter requirement. A delegated effect token must be admitted by a resource guard configured for that
target's audience and scope; the handle re-checks with the scopes the caller passes.

Tests: `CallerAuthorityTest` (11): positive user/operator path, expiry crossed, missing scope, dev headers and hand-built
callers refused, resolved bearer keeps `exp`, delegated positive with one admission, grant revoked after admission, expiry,
unheld scope, verifier/DB outage, a recheck that itself crosses expiry. Each refusal is an exception, so a caller that
checks before mutating mutates nothing.

## 2. Manual-decision policy (request 2)

`Pep.InstanceOperation.RESOLVE_EFFECT` = `operation:resolve-effect`; Cedar rule `operations.resolve-effect` in
`policy/operations/operations.cedar` requires scope `oa.recover` for a `User`. `oa.operate` (retry, recover), `oa.inspect`,
no scope and service principals are denied. It is not a safe-recovery operation, so an unavailable engine is ERROR and
nothing changes. Snapshot is now `2026-10-20.3`. Tests: `ResolveEffectPolicyTest` (real Cedar), `PepInstanceOperationTest`.
Instance/tenant ownership is checked by the caller before `Pep.instanceOperation(RESOLVE_EFFECT, …, instanceId)` (the
request's task id carries the instance, as for the other instance operations).

## 3. Central audit (request 3)

Not done here; it needs the delivery shape agreed first. Proposal for GPT to confirm: `AuditEvent` per transition
(intent, dispatch, unknown, outcome, manual, compensation) with attributes `effect.scope` (tenant + instance + owner digest),
`effect.keyFingerprint`, `effect.transition`, `effect.sequence`, `policy.*` from the PEP decision, and a safe reason code.

and must be accepted idempotently. No payloads, credentials, reply bodies or free error text. GPT owns the outbox and SQL;
