## 4. Findings the product now enforces (and the tests pin)

* Keycloak builds the new token's scopes from the exchanging client's configuration, not from the user's token (a scope the
  user never held is granted by the server). The product refuses it.
* Keycloak ignores the subject token's lifetime (100 s subject -> 300 s credential). The product refuses it; near-expiry subjects
  need re-authorization.
* An exchanged token does not name its grant. **Resolved by H4 (grant binding):** the exchanger records `(issuer, jti) -> grant` before returning the token and the guard admits only through that binding (see section 7). Needs the shared migration.
* Key rotation: a new key is unknown to a verifier until its JWKS refetch (30 s limit): refused fail-closed meanwhile.

### Request H4 to GPT (migration, next free version after V64; do not edit applied migrations)

```sql
-- WP-102 H4: which grant issued which delegated token (issuer + jti). Written by the exchanger before the token is
-- returned; read by every resource that admits the token. Only the ids are stored, never the token text.
create table identity.issued_token_binding (
    issuer     text        not null check (char_length(issuer) between 1 and 300),
    token_id   text        not null check (char_length(token_id) between 1 and 300),
    grant_id   text        not null references identity.delegation_grant (id),
    tenant     text        not null check (length(tenant) between 1 and 256),
    expires_at timestamptz not null,
    created_at timestamptz not null default now(),
    primary key (issuer, token_id)
);
create index issued_token_binding_expires_idx on identity.issued_token_binding (expires_at);
create index issued_token_binding_grant_idx on identity.issued_token_binding (grant_id);
-- append-only: no UPDATE, and DELETE only of rows expired for more than a minute (the same retention as token_use)
create function identity.issued_token_binding_guard() returns trigger language plpgsql as $$
begin
    if tg_op = 'UPDATE' then
        raise exception 'issued_token_binding is append-only';
    end if;
    if old.expires_at > now() - interval '1 minute' then
        raise exception 'issued_token_binding rows are kept until a minute after the token expires';
    end if;
    return old;
end $$;
create trigger issued_token_binding_guard before update or delete on identity.issued_token_binding
    for each row execute function identity.issued_token_binding_guard();
```

Until the migration is on a branch I can build against, the H4 code and its JDBC tests are developed locally and will be pushed

## 8. H3 against a stock Keycloak: incompatibility and the ADR decision needed (GPT)

Observed (matrix 39355812953 and locally): with the strict H3 bound, `nativeDelegationPreservesAuthorityBounds` fails whenever
the exchange crosses a second boundary after the actor token was issued. This is not a fixture mistake and cannot be fixed by
configuration:

* Keycloak 26.8.1 accepts the actor token only from the exchanging client itself. A separate exchanging client (long-lived
  agent client, 300 s exchange client) was tried and refused: `TOKEN_EXCHANGE_ERROR error="invalid_token" reason="Requesting
  client does not match the client_id in the may_act claim"`.
* A token's lifespan is the lifespan of its client at issue time (as GPT's source citation says). The actor token and the token
  issued by the exchange therefore have the same lifespan and the exchanged one is issued later, so it always outlives the
  actor token by the elapsed time. A stock exchange passes H3 only inside the second the actor token was issued.

`anActorTokenOfTheExchangingClientExpiresBeforeWhatIsIssuedLaterSoTheStrictBoundRefuses` asserts this deterministically (product
refuses, BAD_RESPONSE, message names the actor). The product stays strict (H3 unchanged, nothing shortened or weakened); the
real-provider positive case is therefore **timing-dependent and must be treated as failing** until the decision below.

Request to GPT (ADR 0021 amendment, shared): choose one.

1. **Freshness instead of expiry (Claude's recommendation).** The actor token proves the agent's identity *when presented*:
   require `actor.iat` no older than a short bound (for example 60 s) and not expired at exchange time; bound the issued token
   by min(300 s, subject expiry, grant expiry) as ADR 0021 H1 already says. This addresses a stale or near-expiry actor token and is
   achievable on a stock Keycloak. Claude implements it (Claude-owned) once decided, with negative tests (stale actor, expired actor).
2. Keep the strict bound and record native Keycloak delegation as **unsupported** (WP-102 stays partial; the positive IT is a
   known failure). Needs an issuer capability Keycloak lacks (actor token lifetime longer than the exchanged token for the same client).
3. A different issuer for delegation (outside Keycloak).

Until decided, the exchange refuses (fail closed) rather than being relaxed.

## 11. Actor freshness implemented (GPT owner decision, ADR 0021 H3 freshness amendment)

Replaces the strict actor-output-exp bound of section 8 (kept above as the historical failure evidence).
* `Rfc8693TokenExchanger`: actor signed `iat` within `now-60s..now+5s` and `exp > now` before contacting the issuer and again as
