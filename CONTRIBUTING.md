# Contributing

This guide covers building, testing, the module structure and the rules that CI enforces. The architecture decisions are in [docs/adr](docs/adr/README.md), the plan in [docs/plan](docs/plan/README.md).

## Prerequisites

- Java 21 and Maven 3.9 or later (the build enforces both).
- Python 3 (for the generators and the policy checks; standard library only).
- PostgreSQL 16 on `localhost:5432` for the tests, or Docker to run the compose file.

## Local PostgreSQL

The tests and the application use the database `agentic` with user and password `postgres`.

```bash
docker compose up -d                 # starts postgres:16 on :5432 with that database
```

Without Docker, any local PostgreSQL 16 with the same database and credentials works. The tests do not use Testcontainers, so no container daemon is needed.

## Build and test

Run these from the repository root:

```bash
mvn -B verify                                              # all modules: compile, unit and boot tests
python3 tools/render_requirements.py --check               # generated documents match their JSON source
python3 tools/check_dependency_policy.py                   # after mvn verify: contracts purity, licence allow-list
python3 -m unittest discover -s tools -p 'test_*.py' -v    # tests for the policy check
docker compose -f docker-compose.yml config --quiet        # the dev compose file is valid
java -cp "oa-testkit/target/classes:$(cat oa-testkit/target/classpath.txt)" \
  io.github.bassemzohdy.openworkflow.agentic.testkit.acceptance.AcceptanceStatus --check   # after mvn verify: status matches the build
```

CI runs the same checks (see `.github/workflows/build.yml`); the policy check needs the output of `mvn verify`.

To run the application locally:

```bash
mvn -B install -DskipTests          # once, so app-runtime can resolve oa-runtime
cd app-runtime && mvn quarkus:dev
```

## Modules and their relationships

| Module | Packages | May depend on | Rule |
|---|---|---|---|
| `oa-contracts` | `...agentic.contracts` | JDK only (test dependencies allowed) | No compile-time framework dependency. Checked by ArchUnit and by the dependency policy. |
| `oa-runtime` | `...agentic.runtime` | `oa-contracts` and framework libraries | Never depends on `oa-control`. Checked by ArchUnit. |
| `oa-control` | `...agentic.control` | `oa-contracts` | Administration (skeleton). |
| `oa-eval` | `...agentic.eval` | `oa-contracts` | Evaluation (skeleton). |
| `oa-testkit` | `...agentic.testkit` | `oa-contracts`, `oa-runtime` | Test support: acceptance annotation and status generator, scripted model, fault injection, fake IdP and policy service. Used from tests only; never depends on `oa-control`, and does not start Quarkus. See [docs/testing.md](docs/testing.md). |
| `app-runtime` | (deployable) | `oa-runtime`; `oa-testkit` (test) | Runnable Quarkus application: configuration, workflow definitions, boot tests (`*Test`), and process-level tests run after package (`*IT`, failsafe). |
| `app-control` | (deployable) | `oa-control` | Administration deployable (skeleton). |

The runtime keeps working without the control application (ADR 0017). Keep it that way: a runtime class must not reference a control class, even indirectly through a shared type.

## API conventions

These apply to every REST endpoint. The types live in `oa-contracts`, the HTTP mapping in `oa-runtime`.

- **Errors** are RFC 9457 problem documents (`application/problem+json`) from `ProblemDetailMapper`. Server errors return a generic detail; the cause is logged under the correlation id.
- **Correlation id**: `X-Correlation-Id` is read or generated by `CorrelationIdFilter`, placed in the logging context and echoed on every response. An invalid client value is replaced, never echoed.
- **Identifiers** are ULIDs (`Ulid`, `UlidGenerator`): sortable by creation time, no dependency.
- **Pagination** uses an opaque cursor and `PageRequest`: limit at least 1, capped at 200.

## Dependencies and licences

- Add a dependency only with a clear need. Prefer the Quarkus BOM and the versions already managed in the parent POM.
- Licences: Apache-2.0, MIT, MIT-0, BSD, EPL-2.0 and Public Domain (including CC0) are allowed in any scope. CDDL, GPL-2.0 with the Classpath Exception, UPL, MPL-2.0 and LGPL are allowed in test scope only. GPL, AGPL and EPL-1.0 are not allowed. A dual-licensed component passes when one of its licences is allowed. The check reads each POM's licence and tells you which name it could not classify.
- An artifact whose POM declares no licence can be added to `tools/dependency-policy-exceptions.json` after its licence is verified from its own metadata. Entries are reviewed, scoped, and fail the build when stale or marked `unverified`.
- The Maven enforcer enforces Java 21, Maven 3.9 and no duplicate dependency declarations.

## Definition of done for a work package

From [docs/plan/README.md](docs/plan/README.md), section 7:

1. The requirements and tests listed for the package are met. Owned tests are automated and green in CI.
2. Contracts are in `oa-contracts`; no framework leaks into them.
3. Failure behaviour is specified and tested: timeout, crash, duplicate, denial.
4. Audit events, metrics and traces exist for new decisions and effects.
5. Configuration is documented and the defaults are safe (deny, off, bounded).
6. An ADR is written or updated for any decision that is hard to reverse.
7. The generated documents under `docs/` are regenerated and the traceability shows the new status.

## Generated documents

`docs/requirements/README.md`, `docs/test-cases.md`, `docs/traceability.md` and `docs/plan/work-packages.md` are generated. Their sources are the JSON files next to them. Do not edit the generated Markdown by hand.

After changing a JSON source, run:

```bash
python3 tools/render_requirements.py
```

CI runs the same script with `--check` and fails if the committed Markdown differs from what the JSON produces.

## Tests and the status of acceptance tests

Acceptance tests (T01 to T39) are described in [docs/test-cases.md](docs/test-cases.md). A test counts as done only when it is automated, runs in CI, and carries its requirement IDs. Status is recorded in `docs/requirements/test-status.json`; documents must not claim more than the build proves.

To automate a test, annotate it with `@Acceptance("T06", requirements = {"M02"})` from `oa-testkit`. Then run the generator (the command is in the build section above, without `--check`) to record a passing test; CI fails if a recorded automated test regresses. The annotation, the generator, the test doubles and their limits are described in [docs/testing.md](docs/testing.md).
